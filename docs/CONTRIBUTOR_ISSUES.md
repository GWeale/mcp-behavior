## 1. Add a binary file comparison example

Labels: `good first issue`, `tests`, `effects`

Create a small MCP tool that writes a deterministic binary file and verify it with a `file` observer using `compare.kind: bytes`. The example should also show the first changed byte when the candidate is wrong.

Acceptance:

- The matching scenario exits `0` from a clean wheel install.
- A deliberate one-byte change exits `1` and reports the correct byte offset.
- The fixture uses a short generated byte sequence and no checked-in binary blob.

## 2. Add an expected MCP error example

Labels: `good first issue`, `documentation`, `examples`

Create a small example tool that returns an MCP tool error for an invalid ID and a contract with `expect.outcome: error`. Explain the difference between an expected tool error (`MATCH`) and a broken connection (`INCONCLUSIVE`).

Acceptance:

- The example exits `0` from a clean wheel install.
- No credentials or external services are required.
- The example is added to the packaged smoke matrix.

## 3. Add Unicode filename observer coverage

Labels: `good first issue`, `tests`, `cross-platform`

Add an integration fixture that creates and observes a UTF-8 filename on Windows, macOS, and Linux. Exercise both a direct file observer and a tree snapshot.

Acceptance:

- The scenario returns `MATCH` on all three CI operating systems.
- Tree ordering remains deterministic when ASCII and Unicode names are mixed.
- The fixture documents any normalization behavior caused by the host filesystem.

## 4. Add authenticated Streamable HTTP documentation

Labels: `good first issue`, `documentation`, `http`

Document a local HTTP fixture that requires an authorization header supplied through `from_env`. Show how evidence redaction can be checked without printing the token.

Acceptance:

- The documentation uses a fake environment-variable name and no literal credential.
- The example includes a negative missing-variable case.
- Every new local link passes `scripts/check_docs.py`.

## 5. Design controlled repeat runs

Labels: `enhancement`, `design`, `reliability`

Write an ADR for the first roadmap item. Define contract syntax, attempt ordering, semantic evidence, verdict aggregation, and the distinction between flaky behavior and execution uncertainty.

Acceptance:

- The ADR includes at least two interface designs and one caller example for each.
- Identical deterministic attempts have one stable summary digest.
- The design does not classify timeouts as verified behavioral divergence.

## 6. Prototype Docker-backed isolation

Labels: `enhancement`, `prototype`, `security`

Build a throwaway prototype that runs one existing stdio example in a container with a declared workspace mount and environment allowlist.

Acceptance:

- The prototype documents its threat boundary and host prerequisites.
- The default local runner is unchanged.
- The issue reports startup cost and cleanup behavior on success and timeout.

## 7. Specify a read-only Postgres observer

Labels: `enhancement`, `design`, `effects`

Compare two designs: a built-in observer and a custom-probe recipe. Cover deterministic row ordering, credential references, transaction isolation, output bounds, and a local test dependency.

Acceptance:

- The proposal states why a new runtime dependency is or is not justified.
- Queries cannot mutate the database.
- The evidence shape is compatible with existing comparison rules.

## 8. Define the extension SDK stability boundary

Labels: `enhancement`, `design`, `api`

Collect two concrete external observer or comparator implementations and identify their shared interface. Do not publish a generic plugin API from one hypothetical adapter.

Acceptance:

- The proposal includes versioned JSON-compatible inputs and outputs.
- Secret sanitization and output bounds stay owned by the core.
- Failure mapping to `DIVERGE` versus `INCONCLUSIVE` is explicit.
